# Псевдоразметка пар объявлений для картиночного поиска дубликатов — дизайн

Дата: 2026-10-23. Ветка: `pseudo-labeling-loop` репозитория `turkunov/catalogDiff`.

Пометки: **[решено]** — решение пользователя; **[решение дизайна]** — выбрано при проектировании, пользователь может пересмотреть. Без пометки — факты о текущем состоянии.

## 1. Зачем

Нужна псевдоразметка пар объявлений: насколько на двух объявлениях один и тот же товар, по шкале 1–5. Разметчик — большая VLM, которая видит и фото, и текст объявлений (заголовок, описание, параметры). Текст — подсказка учителю, которой у ученика не будет: на этой разметке учатся модели, работающие **только по фото** (картиночный энкодер для поиска кандидатов, позже — голова для финального решения).

Разметка делается циклом из нескольких итераций [решено]: энкодер находит кандидатов → разметчик их оценивает → на разметке (вне проекта) учится следующая версия энкодера → её чекпоинт подаётся в следующую итерацию. Самые ценные пары — где энкодер ставит кандидата высоко, а разметчик говорит «не тот товар» (трудные негативы), и где одинаковый товар энкодер поставил низко (пропущенные позитивы).

## 2. Отправная точка

  - шаг 2 «match»: 2 фото + категория, список ключевых параметров, заголовки+описания, готовые ключевые параметры, атрибуты шага 1 → JSON `{"reasoning", "Класс"}` по каскаду 1–5;

Локальные правки — `repo/docker-compose.override.yml`. Порты только на 127.0.0.1.

## 3. Цели

### 3.1 Одна итерация цикла

Входы итерации: профиль категории, данные двух сторон (A — объявления-запросы, B — каталог кандидатов), чекпоинт энкодера, модель разметчика, бюджет пар на разметку, доли слоёв, порог позитива, параметры лёгких негативов, критерий остановки.

1. **Эмбеддинги.** Картиночная часть энкодера, L2-нормировка, кэш эмбеддингов по (версия энкодера, картинка).
2. **Кандидаты.** Для каждого объявления A — точный поиск по косинусу среди B на GPU, топ-1000, только внутри соответствия категорий из профиля. Приближённый индекс не нужен (≈160 тыс. картинок B для диванов).
3. **Отбор пар на разметку по слоям выдачи** [решено], доли от бюджета — параметры итерации, по умолчанию:

   | Слой (позиция в выдаче) | Доля |
   |---|---|
   | 1–10 | 60% |
   | 11–100 | 25% |
   | 101–1000 | 10% |
   | случайные пары | 5% |

   Плюс **независимый от энкодера источник кандидатов** [решено] — чтобы находить одинаковые товары, которые энкодер поставил низко. Метод — §7. Его доля — тоже параметр.
   Объявления A для итерации выбираются случайно в пределах бюджета [решение дизайна].
4. **Без повторной разметки** [решено]: пара не размечается VLM снова, если у неё уже есть метка той же модели и той же версии профиля.
5. **Разметка** двухшаговым разметчиком (§3.2) — класс 1–5, рассуждение, атрибуты шага 1.
6. **Несогласия** (§3.6) — отбираются в очередь ручной проверки.
7. **Обучающая выборка** — бинаризация по явному порогу + лёгкие негативы (§3.5), экспорт.
8. **Отчёт итерации** (§3.8).

Обучение энкодера в проект не входит [решено]: пользователь берёт экспорт, обучает сам и подаёт новый чекпоинт в следующую итерацию.

### 3.2 Профили категорий [решено]

Пайплайн работает с произвольной категорией; всё, что зависит от категории, лежит в профиле, а в коде нет веток по категориям. Профиль содержит:

- название и язык, на котором разметчик пишет рассуждение [решение дизайна];
- соответствие категорий сторон A и B (фильтр при поиске кандидатов);
- схему входных таблиц: какие колонки — id, заголовок, описание, параметры, путь или URL картинки, категория (§7);
- список визуальных атрибутов шага 1;
- список ключевых параметров шага 2 и откуда их брать: из колонки данных или «извлечь из текста»;
- текстовое определение классов 1–5 для этой категории;
- шаблоны промптов шагов 1 и 2: собираются из полей выше, допускают ручную правку;
- примеры пар для вкладки разметки.

Профиль версионируется: любое изменение — новая версия; каждая метка ссылается на версию профиля.

- **«Диваны» v1** — текущие промпты `STRICT_PROMPT_TEMPLATE` и `MATCH_PROMPT_TEMPLATE` из `run_qwen3_vl_batch.py` **без изменений**, на русском, с теми же параметрами генерации (match: temperature 0.1, top_p 0.3, max_tokens 1024, json_object; strict: temperature 0) — чтобы результаты были сравнимы с уже полученными [решение дизайна]. Все эксперименты — только на диванах [решено].
- **Демо-профили «Hoodies» и «Cars»** [решено] — без экспериментов, по 3 примера пар на разные уровни совпадения [решено]: ожидаемый класс ~5, ~3 и ~1–2 [решение дизайна]. Пары подбирает исполнитель из публичных объявлений [решено]; картинки хранятся локально вместе с демо, не ссылками [решение дизайна]. Худи — Avito↔Ozon; машины — Avito↔Avito, потому что Ozon машины не продаёт [решение дизайна]. Язык рассуждения — английский [решение дизайна]. Ожидаемый класс в примере — суждение исполнителя; демо показывает, что поставил разметчик, примеры под ответ не подгоняются.
  Атрибуты шага 1 [решение дизайна]: худи — цвет, принт/логотип, капюшон, молния, крой; машины — марка и модель, тип кузова, цвет, поколение по внешнему виду.

### 3.3 Энкодер [решено]

- По умолчанию SigLIP2 `google/siglip2-so400m-patch14-384` [модель — решение дизайна]. Чекпоинт задаётся id на Hugging Face или локальным путём в формате `save_pretrained`, чтобы подавать дообученные версии.
- Используется только картиночная часть; текстовая не используется.
- Головы в v1 нет, решения по кандидатам — по косинусу. В конфиге и интерфейсе оставлен необязательный слот «голова»: если она есть, переоценивает кандидатов, и слои строятся по её оценке. В v1 не реализуется.
- Версия энкодера (имя/путь + хэш чекпоинта) хранится с каждой парой.

### 3.4 Хранилище меток и версии [решено]

Ключ пары: (профиль, id A, id B). На каждую разметку — отдельная запись:

- **результат:** сырой класс 1–5, рассуждение, сырые ответы обоих шагов, атрибуты шага 1, время, ошибка;
- **происхождение пары:** итерация, версия энкодера, слой, позиция в выдаче, косинус, (оценка головы);
- **кто разметил:** тип (VLM / человек), модель, версия профиля, параметры генерации, дата; для человека — комментарий.

Человеческие метки хранятся отдельно и никогда не перезаписываются VLM. Существующие `qwen_labels_out.csv` и метки `small` импортируются как «legacy» для справки и отбора ручного теста, в экспорт по умолчанию не попадают [решение дизайна].

### 3.5 Бинаризация и экспорт [решено]

- **Порог позитивного класса задаётся пользователем явно; значения по умолчанию нет.** Без порога экспорт, несогласия и бинарные метрики не считаются, пайплайн сообщает, что порог не задан.
- Веса классов настраиваемые, по умолчанию все равны 1 [решение дизайна].
- Сырой класс 1–5 сохраняется всегда; бинарная метка — производная.
- **Лёгкие негативы:** случайные пары объявлений A и B внутри соответствующих категорий, VLM их не размечает, в экспорте помечены как `auto_negative` [решено]. Их число — параметр итерации. Небольшая доля (по умолчанию 2%) всё же проходит через VLM, чтобы оценить шум [решение дизайна].
- **Экспорт** (Parquet и CSV): id A, id B, пути к картинкам, сырой класс, бинарная метка, вес, источник метки (vlm / human / auto_negative / legacy), слой, итерация, версия энкодера и профиля. Если у пары есть человеческая метка — используется она.

### 3.6 Несогласия [решено: ручная проверка несогласий]

Определение [решение дизайна]: энкодер «считает пару позитивом», если она в слое 1–10. Несогласие — пара из слоя 1–10 с классом ниже порога, либо пара из слоёв 11–1000 или из независимого источника с классом не ниже порога. Ручной проверке отдаётся выборка несогласий; размер задаёт пользователь.

### 3.7 Ручной тест (только диваны, только для экспериментов) [решено]

- 200 пар из `combined_labeled_df_balanced_small`: по 40 на каждый старый класс 1–5, по возможности одна пара на объявление Avito [решение дизайна, принято]. Старая метка нужна только для отбора.
- Человек ставит класс 1–5 вслепую: ответ VLM скрыт до ответа человека.
- Метрики — **только качество разметчика** относительно человека: точное совпадение, ±1, матрица ошибок, точность и полнота бинарной метки при заданном пороге. Энкодер на ручном тесте не оценивается [решено].

### 3.8 Отчёт итерации и остановка [решено]

- По каждому слою и независимому источнику: распределение классов, число позитивов, число несогласий.
- Сравнение с прошлой итерацией.
- Метрики разметчика на ручном тесте, если он есть у профиля (меняются только при смене модели или версии профиля).
- Критерий остановки выбирает пользователь: число итераций, бюджет пар или «новых позитивов + несогласий за итерацию меньше N». Пайплайн сообщает, сработал ли критерий; следующую итерацию запускает пользователь, подав новый чекпоинт.

### 3.9 Приложение (демо) [решено]

Gradio (развитие текущего `gradio_labeling_app.py`), **интерфейс на английском**, пять вкладок:

1. **Profiles** — список профилей, редактор полей, просмотр собранных промптов и ручная правка, версии, «проверить на примере».
2. **Pair labeling** — профиль + готовый пример или два своих объявления (фото, заголовок, описание, параметры) → атрибуты шага 1, рассуждение, класс, бинарная метка при выбранном пороге, время.
3. **Iterations** — параметры итерации (§3.1), запуск, прогресс и ETA, таблица итераций с отчётами, экспорт обучающей выборки.
4. **Manual review** — очереди «manual test» и «disagreements of iteration N», слепая разметка 1–5 и комментарий, прогресс.
5. **Labels** — просмотр хранилища с фильтрами (профиль, итерация, слой, класс, модель, версия профиля, несогласие, человек/VLM/auto/legacy), карточка пары, экспорт выбранного.

Метрики разметки по-прежнему уходят в Prometheus и Grafana [решение дизайна].

## 4. Не цели

- Обучение энкодера и головы.
- Оценка энкодера на ручном тесте, Recall@k по каталогу.
- Эксперименты на худи и машинах.
- Флаг «различимо ли отличие по фото» (предложен, отклонён).
- Многопользовательский режим, авторизация, прод-сервинг.

## 5. Анти-цели (провал, даже если всё формально работает)

- Неявное значение порога позитива.
- Категорийная логика в коде вместо профиля.
- Повторная разметка пар без смены модели или профиля — пустая трата GPU.
- Человек видит ответ VLM до своего.
- Тихая правка промптов «Диваны» v1 — ломает сравнимость; менять только новой версией профиля.
- Приложение доступно не только через 127.0.0.1 (Jupyter и Gradio без пароля).

## 6. Ограничения и среда

- Сервер `avi-gn-fsk44`: 8×H100 80GB, общие с другими пользователями (на 2026-10-22 GPU 3–6 заняты чужими процессами); наш vLLM — GPU 7, занимает 90% памяти, поэтому SigLIP2 считается на другом свободном GPU [решение дизайна]. Номера GPU — параметры конфига.
- Узел в Slurm в состоянии `drain`; запуск — напрямую через docker compose, как сейчас.
- Пропускная способность разметчика ≈ 420 пар/ч на GPU (27B, 4 потока); бюджет итерации задаётся в парах с этим расчётом. Масштабирование — дополнительные реплики vLLM на свободных GPU [решение дизайна, опционально].
- Qwen3.5 по умолчанию «думает»; в «Диваны» v1 это не трогаем.
- Тексты объявлений — на русском.
