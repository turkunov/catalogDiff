# Псевдоразметка пар объявлений для картиночного поиска дубликатов — дизайн

Дата: 2026-10-23. Ветка: `pseudo-labeling-loop` репозитория `turkunov/catalogDiff`.

Пометки: **[решено]** — решение пользователя; **[решение дизайна]** — выбрано при проектировании, пользователь может пересмотреть. Без пометки — факты о текущем состоянии.

## 1. Зачем

Нужна псевдоразметка пар объявлений: насколько на двух объявлениях один и тот же товар, по шкале 1–5. Разметчик — большая VLM, которая видит и фото, и текст объявлений (заголовок, описание, параметры). Текст — подсказка учителю, которой у ученика не будет: на этой разметке учатся модели, работающие **только по фото** (картиночный энкодер для поиска кандидатов, позже — голова для финального решения).

Разметка делается циклом из нескольких итераций [решено]: энкодер находит кандидатов → разметчик их оценивает → на разметке (вне проекта) учится следующая версия энкодера → её чекпоинт подаётся в следующую итерацию. Самые ценные пары — где энкодер ставит кандидата высоко, а разметчик говорит «не тот товар» (трудные негативы), и где одинаковый товар энкодер поставил низко (пропущенные позитивы).

**Что делаем сейчас** [решено]:
- эксперименты — только оценка разметчика на 200 парах диванов с ручной разметкой (§3.9);
- механика итераций строится целиком и работает, но реальный сценарий не имитирует: обучения нет, данные — только `small` (§3.1);
- сравнивать с прежними результатами (70% совпадения и т. п.) не нужно — всё, включая промпты, делается полноценно, без оглядки на старые прогоны.

## 2. Отправная точка

- **Код (catalogDiff, ветка main).** `notebooks/run_qwen3_vl_batch.py` — двухшаговый разметчик через OpenAI-совместимый API vLLM:
  - шаг «strict», на пару: 2 фото + промпт → JSON с визуальными атрибутами каждого товара (для диванов: цвет, форма, обивка, накрыт ли);
  - шаг «match», на пару: 2 фото + категория, список ключевых параметров, заголовки+описания, готовые ключевые параметры, атрибуты шага strict → JSON `{"reasoning", "Класс"}` по каскаду 1–5;
  - `notebooks/gradio_labeling_app.py` — Gradio с пулами задач; Prometheus + Grafana для метрик разметки.
- **Известные проблемы промпта match для диванов:** просит «игнорировать различия в цвете», хотя «основной цвет» — ключевой параметр; правило «на первом критичном «нет» верни предыдущий класс» расходится со стрелками каскада; шаг В4 описан дважды.
- **Развёртывание.** Сервер `avi-gn-fsk44`, каталог `/data/mvlsmirnov/catalogDiff` (инструкция `RUN_AVI44.md`). vLLM с `Qwen/Qwen3.5-27B` на GPU 7, образ `catalogdiff/vllm-openai:v0.32.0-cu129-fix` (сборка из `vllm-cu129/Dockerfile`: в официальном `v0.32.0-cu129` torchcodec собран под CUDA 13, заменён на CPU-сборку), `NVIDIA_DISABLE_REQUIRE=1` (драйвер 560 = CUDA 12.6, работает через forward compat). Локальные правки — `repo/docker-compose.override.yml`. Порты только на 127.0.0.1.
- **Данные (диваны, задача DSSWAT-20021)** в `/data/mvlsmirnov/catalogDiff/data`. Ссылки на картинки Ozon в данных отдают 404 — работаем только с локальными файлами.
- **Замеры Qwen3.5-27B** (с «размышлениями», как по умолчанию): шаг strict 15–24 с, шаг match 8–10 с на пару на поток; 4 потока на одной H100 ≈ 7 пар/мин при двух шагах на пару. Qwen2.5-VL-7B заметно хуже по качеству; не используем.

## 3. Цели

### 3.1 Данные v1 [решено]

Считаем, что данные есть только в `train_test_with_images/combined_labeled_df_balanced_small.csv`: 6 394 пары, 1 687 объявлений Avito, 5 447 товаров Ozon. У каждого объявления есть картинка (распакована в `data/images_small`), заголовок, описание и готовые ключевые параметры (`q_key_params` / `d_key_params`: обивка, форма, цвет; привязаны к объявлению, а не к паре; у Ozon часть значений пустая). Полные `avito_items.csv` / `ozon_items.csv` и `assessment/` не используются.

Пайплайн при этом не привязан к `small`: структура входа задаётся профилем (§3.4), и другие файлы той же или описанной в профиле структуры подаются так же.

### 3.2 Одна итерация цикла

Входы итерации: профиль категории, файл пар, режим получения пар, чекпоинт энкодера, модель разметчика, бюджет пар на разметку, доли слоёв, порог позитива, параметры лёгких негативов, необязательный список исключаемых объявлений A (по умолчанию пустой) [решение дизайна], критерий остановки.

**Вселенная итерации** — объявления из файла пар: сторона A (запросы, `q_*`) и сторона B (кандидаты, `d_*`).

**Два режима получения пар** [решено], оба работают на `small`:

1. **Готовые пары из файла** — по умолчанию в демо. Пары берутся из файла как есть.
2. **Поиск кандидатов энкодером** внутри вселенной: для объявления A — все объявления B (для `small` это 1 687 × 5 447), ранжированные по косинусу, топ-1000.

Шаги:

1. **Эмбеддинги** картиночной частью энкодера (§3.5), L2-нормировка, кэш по (версия энкодера, картинка).
2. **Позиция в выдаче.** Для каждой пары — косинус и место объявления B в ранжировании всех объявлений B вселенной для этого A [решение дизайна]. В режиме 1 это делает слои осмысленными, а не «все пары в топ-10».
3. **Отбор пар на разметку по слоям** [решено], доли от бюджета — параметры итерации, по умолчанию:

   | Слой (позиция в выдаче) | Доля |
   |---|---|
   | 1–10 | 60% |
   | 11–100 | 25% |
   | 101–1000 | 10% |
   | случайные пары | 5% |

   Если в слое не хватает пар, остаток бюджета делится между остальными слоями пропорционально [решение дизайна]. Объявления A выбираются случайно [решение дизайна].
   **Независимый от энкодера источник кандидатов** [решено] — в режиме 2: близость заголовков внутри вселенной (§7). Его доля — параметр.
4. **Без повторной разметки** [решено]: пара не размечается VLM снова, если у неё уже есть метка той же модели и той же версии профиля.
5. **Разметка** (§3.3).
6. **Несогласия** (§3.8) — выборка в очередь ручной проверки.
7. **Обучающая выборка** — бинаризация по явному порогу + лёгкие негативы (§3.7), экспорт.
8. **Отчёт итерации** (§3.10).

Обучения нет [решено]: пользователь берёт экспорт и при желании обучает сам; следующая итерация принимает новый чекпоинт энкодера.

### 3.3 Разметчик: три шага [решено]

Все шаги выполняет одна модель (по умолчанию Qwen3.5-27B — она понимает и картинки, и текст); отдельной текстовой LLM нет.

1. **Визуальные атрибуты — на объявление, только картинка.** Фото одного объявления → визуальные атрибуты из профиля. Текст в этот вызов не подаётся, чтобы атрибуты были независимой проверкой и не повторяли заголовок (если заголовок говорит «угловой», а на фото прямой — атрибут должен сказать «прямой»). Результат кэшируется как свойство объявления.
2. **Параметры из текста — на объявление, только текст.** Заголовок и описание → недостающие ключевые параметры; готовые значения не трогаются; если все параметры заполнены, вызова нет. Результат кэшируется как свойство объявления.
3. **Сопоставление — на пару.** Обе картинки, оба текста, ключевые параметры (готовые + из шага 2), визуальные атрибуты из шага 1 → рассуждение и класс 1–5.

Кэш на объявление хранит версию модели и профиля; при их смене шаги 1–2 для объявления пересчитываются. Отличие от исходного кода: описание фото делается один раз на объявление, а не на каждую пару, и без текста.

Параметры генерации — в профиле; значения по умолчанию [решение дизайна]: шаги 1–2 — temperature 0; шаг 3 — temperature 0.1, top_p 0.3, max_tokens 1024, JSON-ответ. Включать ли «размышления» Qwen3.5 — настройка профиля, по умолчанию включены (как сейчас); выбор делается по ручному тесту [решение дизайна].

### 3.4 Профили категорий [решено]

Пайплайн работает с произвольной категорией; всё, что зависит от категории, лежит в профиле, а в коде нет веток по категориям. Профиль содержит:

- название и язык, на котором разметчик пишет рассуждение [решение дизайна];
- соответствие категорий сторон A и B (фильтр кандидатов; для `small` не нужен — там одна категория);
- схему входа: какие колонки файла пар — id, заголовок, описание, ключевые параметры, путь или URL картинки, категория — для каждой стороны;
- список визуальных атрибутов (шаг 1);
- список ключевых параметров и колонка с готовыми значениями, если есть (недостающие заполняет шаг 2);
- текстовое определение классов 1–5 для этой категории;
- шаблоны промптов трёх шагов: собираются из полей выше, допускают ручную правку;
- параметры генерации и настройка «размышлений»;
- примеры пар для вкладки разметки.

Профиль версионируется: любое изменение — новая версия; каждая метка ссылается на версию профиля.

- **«Диваны»** — промпты строятся на основе текущих `STRICT_PROMPT_TEMPLATE` и `MATCH_PROMPT_TEMPLATE`, но переписываются полноценно под новую схему (атрибуты по одному фото, параметры из текста, сопоставление) и без известных противоречий [решено: делать полноценно; конкретные правки — решение дизайна]:
  - цвет — ключевой параметр и сравнивается, а не игнорируется; из правил нормализации убираются нерелевантные для мебели единицы (ГБ, мА·ч и т. п.);
  - каскад классов задаётся однозначно (одна логика переходов, без «верни предыдущий класс» поверх стрелок, без дублей шагов);
  - определения классов 1–5 записываются в профиль явно.
  Ключевые параметры — из `q_key_params` / `d_key_params`, недостающие — шагом 2. Все эксперименты — только на диванах [решено].
- **Демо-профили «Hoodies» и «Cars»** [решено] — без экспериментов, по 3 примера пар на разные уровни совпадения [решено]: ожидаемый класс ~5, ~3 и ~1–2 [решение дизайна]. Пары подбирает исполнитель из публичных объявлений [решено]; картинки хранятся локально вместе с демо, не ссылками [решение дизайна]. Худи — Avito↔Ozon; машины — Avito↔Avito, потому что Ozon машины не продаёт [решение дизайна]. Готовых параметров нет — их заполняет шаг 2. Язык рассуждения — английский [решение дизайна]. Ожидаемый класс в примере — суждение исполнителя; демо показывает, что поставил разметчик, примеры под ответ не подгоняются.
  Визуальные атрибуты [решение дизайна]: худи — цвет, принт/логотип, капюшон, молния, крой; машины — марка и модель, тип кузова, цвет, поколение по внешнему виду.

### 3.5 Энкодер [решено]

- По умолчанию SigLIP2 `google/siglip2-so400m-patch14-384` [модель — решение дизайна]. Чекпоинт задаётся id на Hugging Face или локальным путём в формате `save_pretrained`, чтобы подавать дообученные версии.
- Используется только картиночная часть.
- Головы в v1 нет, решения по кандидатам — по косинусу. В конфиге и интерфейсе оставлен необязательный слот «голова»: если она есть, переоценивает кандидатов, и слои строятся по её оценке. В v1 не реализуется.
- Версия энкодера (имя/путь + хэш чекпоинта) хранится с каждой парой.

### 3.6 Хранилище меток и версии [решено]

- **Объявления:** визуальные атрибуты (шаг 1) и параметры из текста (шаг 2) с версией модели и профиля.
- **Пары:** ключ (профиль, id A, id B). На каждую разметку — отдельная запись:
  - результат: сырой класс 1–5, рассуждение, сырой ответ шага 3, время, ошибка;
  - происхождение пары: итерация, режим, версия энкодера, слой, позиция в выдаче, косинус, (оценка головы);
  - кто разметил: тип (VLM / человек), модель, версия профиля, параметры генерации, дата; для человека — комментарий.

Человеческие метки хранятся отдельно и никогда не перезаписываются VLM. Колонка `label` из `small` импортируется как «legacy»: для справки и для отбора ручного теста, в экспорт по умолчанию не попадает [решение дизайна].

### 3.7 Бинаризация и экспорт [решено]

- **Порог позитивного класса задаётся пользователем явно; значения по умолчанию нет.** Без порога экспорт, несогласия и бинарные метрики не считаются, пайплайн сообщает, что порог не задан.
- Веса классов настраиваемые, по умолчанию все равны 1 [решение дизайна].
- Сырой класс 1–5 сохраняется всегда; бинарная метка — производная.
- **Лёгкие негативы:** случайные пары объявлений A и B из вселенной итерации, VLM их не размечает, в экспорте помечены как `auto_negative` [решено]. Их число — параметр итерации. Небольшая доля (по умолчанию 2%) всё же проходит через VLM, чтобы оценить шум [решение дизайна].
- **Экспорт** (Parquet и CSV): id A, id B, пути к картинкам, сырой класс, бинарная метка, вес, источник метки (vlm / human / auto_negative / legacy), слой, итерация, версия энкодера и профиля. Если у пары есть человеческая метка — используется она.

### 3.8 Несогласия [решено: ручная проверка несогласий]

Определение [решение дизайна]: энкодер «считает пару позитивом», если она в слое 1–10. Несогласие — пара из слоя 1–10 с классом ниже порога, либо пара из слоёв 11–1000 или из независимого источника с классом не ниже порога. Ручной проверке отдаётся выборка несогласий; размер задаёт пользователь.

Слепая проверка [решение дизайна]: на карточке ручной проверки (и несогласий, и ручного теста) скрыты не только класс и рассуждение VLM, но и слой, позиция в выдаче и косинус — по ним угадывается ответ VLM. Видны только два объявления: фото, заголовок, описание, параметры. Контрольные пары не подмешиваются; вкладка Labels не ограничивается.

### 3.9 Ручной тест (только диваны, только для экспериментов) [решено]

Единственная мера качества разметчика. Порядок:

1. **Отбор — заранее и один раз.** 200 пар из `small`: по 40 на каждый старый класс 1–5, по возможности одна пара на объявление Avito [решение дизайна, принято]. Старая метка нужна только для отбора. Набор фиксируется и дальше не меняется.
2. **Ручная разметка.** Человек ставит каждой паре класс 1–5 во вкладке Manual review (вслепую, §3.8); можно также загрузить готовую ручную разметку из CSV [решение дизайна].
3. **Прогон.** Эти 200 пар проходят через тот же пайплайн, что и любые другие, без особой обработки. Каждый новый вариант разметчика (модель, промпт, «размышления») прогоняется на тех же 200 парах; ручная разметка не повторяется.

Метрики — разметчик относительно человека: точное совпадение, ±1, матрица ошибок, точность и полнота бинарной метки при заданном пороге; плюс время на пару. Энкодер на ручном тесте не оценивается [решено].

### 3.10 Отчёт итерации и остановка [решено]

- По каждому слою и независимому источнику: распределение классов, число позитивов, число несогласий.
- Сравнение с прошлой итерацией.
- Метрики разметчика на ручном тесте, если он есть у профиля (меняются только при смене модели или версии профиля).
- Критерий остановки выбирает пользователь: число итераций, бюджет пар или «новых позитивов + несогласий за итерацию меньше N». Пайплайн сообщает, сработал ли критерий; следующую итерацию запускает пользователь.

### 3.11 Приложение (демо) [решено]

Gradio (развитие текущего `gradio_labeling_app.py`), **интерфейс на английском**, пять вкладок:

1. **Profiles** — список профилей, редактор полей, просмотр собранных промптов и ручная правка, версии, «проверить на примере».
2. **Pair labeling** — профиль + готовый пример или два своих объявления (фото, заголовок, описание, параметры) → визуальные атрибуты каждого объявления, параметры из текста, рассуждение, класс, бинарная метка при выбранном пороге, время.
3. **Iterations** — параметры итерации (§3.2), запуск, прогресс и ETA, таблица итераций с отчётами, экспорт обучающей выборки.
4. **Manual review** — очереди «manual test» и «disagreements of iteration N», слепая разметка 1–5 и комментарий, загрузка ручной разметки из CSV, прогресс; для ручного теста — запуск прогона и метрики.
5. **Labels** — просмотр хранилища с фильтрами (профиль, итерация, слой, класс, модель, версия профиля, несогласие, человек/VLM/auto/legacy), карточка пары, экспорт выбранного.

Метрики разметки по-прежнему уходят в Prometheus и Grafana [решение дизайна].

## 5. Анти-цели (провал, даже если всё формально работает)

- Неявное значение порога позитива.
- Категорийная логика в коде вместо профиля.
- Текст объявления попадает в шаг описания фото — визуальные атрибуты перестают быть независимыми.
- Повторная разметка пар или повторное описание объявлений без смены модели или профиля — пустая трата GPU.
- Человек видит ответ VLM до своего.
- Изменение профиля без новой версии — метки перестают быть воспроизводимыми.
- Приложение доступно не только через 127.0.0.1 (Jupyter и Gradio без пароля).

## 6. Ограничения и среда

- Сервер `avi-gn-fsk44`: 8×H100 80GB, общие с другими пользователями (на 2026-10-22 GPU 3–6 заняты чужими процессами); наш vLLM — GPU 7, занимает 90% памяти, поэтому SigLIP2 считается на другом свободном GPU [решение дизайна]. Номера GPU — параметры конфига.
- Узел в Slurm в состоянии `drain`; запуск — напрямую через docker compose, как сейчас.
- Пропускная способность: на пару остаётся один вызов VLM (сопоставление, ~8–10 с на поток по прошлым замерам); описание фото и параметры из текста — один раз на объявление. Бюджет итерации задаётся в парах. Масштабирование — дополнительные реплики vLLM на свободных GPU [решение дизайна, опционально].
- Вселенная `small` маленькая (5 447 картинок B), точный поиск на GPU — секунды.
- Тексты объявлений — на русском (в `small` приведены к нижнему регистру).
- Файлы развёртывания на сервере (`vllm-cu129/Dockerfile`, `repo/docker-compose.override.yml`, `RUN_AVI44.md`) сейчас лежат только на сервере, а закоммиченный `docker-compose.yml` всё ещё поднимает vLLM 0.8.5 с Qwen2.5-VL-7B, публикует порты на всех интерфейсах и держит Grafana с `admin/admin`. В ветке [решение дизайна]: Dockerfile образа vLLM и compose с Qwen3.5-27B и портами на 127.0.0.1 становятся частью репозитория; всё машинно-зависимое (номера GPU, пути к данным, пароль Grafana) задаётся через `.env` и локальный override вне git; инструкция по запуску — в README.
